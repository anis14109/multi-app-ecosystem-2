## 1. About This Guide

This guide reproduces **PHASE 01 — Project Architecture & Route Organization** for a project that
will eventually become a **multi-application ecosystem**:

| Surface       | URL prefix   | Purpose                                        |
|---------------|--------------|------------------------------------------------|
| Public website| `/`          | Frontend pages + dynamic CMS pages             |
| Admin         | `/access/*`  | Protected dashboard, profile, and later modules|
| API           | `/api/v1/*`  | Token-based JSON API (e.g. a Flutter app)      |

The whole phase keeps **Laravel Breeze authentication working unchanged** — we only **re-locate** its
URLs under `/access/*` and **rename one route** (`dashboard` → `admin.dashboard`).

> **Reading rule.** Always run `composer ...` and `php artisan ...` from the Laravel app root.
> In this repository that is `laravel-web-api/apps/`. In a standard fresh install it is simply your
> project root. The setup steps will create that directory for you.

**Every code block below is copied from the real, working implementation** — you can paste them
verbatim.

## 4. Architecture Overview

The goal is a codebase where the three surfaces never mix:

1. **Public frontend** — simple controllers that render Blade views; plus one dynamic CMS route
   `/{slug}` that renders published `Page` records.
2. **Admin dashboard** — everything lives under the `/access` prefix and is protected by the
   `auth` + `verified` middleware. Breeze authentication itself keeps its home under the **same**
   `/access` prefix, but all of Breeze's controllers, views, and route names stay put.
3. **API v1** — a separate route file wired through `bootstrap/app.php`'s `withRouting(api: ...)`
   so it gets the `api` middleware group. Uses **Sanctum personal access tokens** and is
   deliberately **stateless** (independent from Blade session auth).
4. **Route organization** — one route file per concern (`web.php` composes `auth.php` +
   `admin.php` + `frontend.php`; `api.php` composes `api/v1.php`). The **order matters** and is
   what protects the admin and API URLs from the dynamic slug route.

### Why each decision was made

| Decision | Reason |
|----------|--------|
| Put everything under `/access/*` | One obvious, hard-to-guess prefix for the authenticated area; the public website stays the site root. |
| Keep Breeze controllers/views/tests in place | Minimum diff, maximum safety. Renaming them costs time and risks breaking auth; PHASE 01 only needs to *relocate* URLs and *rename one route*. |
| Only rename `dashboard` → `admin.dashboard` | Keeps every other Breeze route name (`login`, `register`, `password.*`, `verification.*`, `profile.*`, `logout`) intact so Blade `route()` calls and existing code keep working. |
| Two separate groups in `routes/auth.php` | Guests and authenticated users already have different middleware needs (`guest` vs `auth`); we keep Breeze's original split and only add the `access` prefix. |
| Separate `routes/admin.php` | Admin resources grow a lot in later phases (students, attendance, menus, pages, website...). A dedicated file keeps that growth out of `web.php`. |
| `routes/api.php` → `routes/api/v1.php` | Versioning at the routing layer: `v2`, `v3`, ... are added without touching `v1`. |
| `api:` in `withRouting(...)` | Gives API routes the framework's `api` middleware group automatically. |
| `api` group stays default (`SubstituteBindings` only) | We deliberately do **not** add `EnsureFrontendRequestsAreStateful`. The API is **token-only**, built for a mobile app (Flutter), not a cookie-based SPA. |
| Dynamic `/{slug}` registered **last**, regex-constrained | Guarantees it can never capture `/access/*`, `/api/*`, `/up`, or the static routes (`/`, `/about`, ...). |
| `pages` table with `status` + `published_at` | Lets CMS editors prepare future pages and schedule publication. |
| No `Services/`/`Actions/` folder yet | Controllers are still thin and each does one small job. Introducing abstraction layers before real reuse/complexity just adds indirection. We add services later only when logic must be shared between controllers/queues/tests. |
| API login logic stays in `Api\V1\AuthController` | It is ~10 lines and used in exactly one place — there is no second consumer yet. Keep it where it is obvious; extract later when (and only when) needed. |
| Stateless `Hash::check` instead of `Auth::attempt` | API login never touches the web session — browser users and API clients are fully isolated. |
| Flat `resources/views/frontend/` (no `frontend/home`, `frontend/pages`, etc.) | Six tiny pages do not need sub-folders; the filename *is* the page identity (`home.blade.php`, `page.blade.php`, ...). Fewer folds = less guesswork, easier expansion later. |
| Shared Blade components live in `auth/components/` | `resources/views/` keeps **exactly three top-level domains** (`admin/`, `auth/`, `frontend/`). The Breeze component kit (inputs, buttons, nav-link, dropdown, modal, ...) is shared between the guest auth pages and the admin chrome, so it lives in the auth domain and is registered via `Blade::anonymousComponentPath('resources/views/auth/components')` — all existing `<x-*>` tags keep resolving unchanged. The frontend nav bar is used by exactly one layout, so it stays a plain partial under `frontend/navigation.blade.php` instead of a component. |
| `phpunit.xml` `APP_URL=http://localhost` | In this repo `APP_URL` contains a sub-folder path; without this override every test URL resolves to `/multi-app-ecosystem-2/.../login` → 404. Tests must always be absolute-URL-agnostic. |

### STEP 1 · Baseline verification + test URL fix

**MODIFY** `APP_ROOT/phpunit.xml` — add the `APP_URL` env line.

**Why:** feature tests build absolute URLs from `config('app.url')`. If that value contains a
sub-folder path, every test route 404s. Overriding it in `phpunit.xml` keeps tests isolated from
your deployment layout (on a standard install this line is harmless).

```xml
<php>
    <env name="APP_ENV" value="testing"/>
    <env name="APP_URL" value="http://localhost"/>
    <env name="DB_CONNECTION" value="sqlite"/>
    <env name="DB_DATABASE" value=":memory:"/>
    ...
</php>
```

Keep the rest of `phpunit.xml` as Breeze generated it (the sqlite `:memory:` block above already
exists by default).

### STEP 3 · Pages migration + Page model

#### 3a. Create the migration

**CREATE** `APP_ROOT/database/migrations/YYYY_MM_DD_HHMMSS_create_pages_table.php`
(placeholder your `now()` timestamp):

```php
<?php

use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    public function up(): void
    {
        Schema::create('pages', function (Blueprint $table): void {
            $table->id();
            $table->string('title');
            $table->string('slug')->unique();
            $table->longText('content')->nullable();
            $table->string('status')->default('draft');
            $table->timestamp('published_at')->nullable();
            $table->timestamps();
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('pages');
    }
};
```

> In this repo the file is `2026_09_23_000001_create_pages_table.php`. If you prefer the artisan
> shortcut: `php artisan make:model Page -m`, then replace the generated migration body with the
> code above.

**What each column is for:**

| Column         | Why                                                               |
|----------------|-------------------------------------------------------------------|
| `title`        | Human-readable heading (also used in `<title>` and the H1).       |
| `slug`         | Public URL segment, `unique` because it is the URL key.           |
| `content`      | `longText` — the page body (HTML). Nullable: a draft may be empty.|
| `status`       | `draft` / `published` workflow state; defaults to `draft`.        |
| `published_at` | Optional scheduling field used by the `published` scope.          |

#### 3b. Create the model

**CREATE** `APP_ROOT/app/Models/Page.php`:

```php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Attributes\Fillable;
use Illuminate\Database\Eloquent\Attributes\Hidden;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Builder;

#[Fillable(['title', 'slug', 'content', 'status', 'published_at'])]
#[Hidden([])]
class Page extends Model
{
    protected function casts(): array
    {
        return [
            'published_at' => 'datetime',
        ];
    }

    public function scopePublished(Builder $query): Builder
    {
        return $query->where('status', 'published')
            ->whereNotNull('published_at')
            ->where('published_at', '<=', now());
    }
}
```

**What each part does:**

- `#[Fillable([...])]` — Laravel 12/13's attribute form of `$fillable`: only these fields can be
  mass-assigned. (If your Laravel version does not have attribute classes, use
  `protected $fillable = ['title', 'slug', 'content', 'status', 'published_at'];` instead.)
- `#[Hidden([...])]` — attribute form of `$hidden`. Empty here; it just keeps the file
  consistent with the default Laravel 13 model style.
- `casts()` → `published_at => 'datetime'` — so `$page->published_at` is a `Carbon` instance.
- `scopePublished(Builder $query)` — reusable query scope that only returns pages that are
  `status = published`, have a `published_at`, and whose `published_at` is not in the future.

**Verify:**
```bash
php artisan migrate
php artisan tinker --execute="dump(App\Models\Page::create(['title'=>'Mission','slug'=>'mission','content'=>'<p>Hi</p>','status'=>'published','published_at'=>now()])->toArray());"
```

### STEP 5 · Restructure the routes

This is the heart of the phase. We create five route files and touch `bootstrap/app.php`.

#### 5a. **MODIFY** `routes/web.php` — become the composer

```php
<?php

use Illuminate\Support\Facades\Artisan;
use Illuminate\Support\Facades\Route;

// *************************************************
// Database Migration Routes (For Development Only)
// *************************************************
Route::middleware('auth.basic')->group(function () {
    // 1. Run Standard Migration (Safe for live data)
    Route::get('/db-migrate', function () {
        Artisan::call('migrate', ['--force' => true]);
        return response("<pre>Database Migrated:\n\n".Artisan::output()."</pre>");
    });
    // 2. Fresh Migration Only (Wipes all data)
    Route::get('/db-fresh', function () {
        Artisan::call('migrate:fresh', ['--force' => true]);
        return response("<pre>Database Wiped & Rebuilt:\n\n".Artisan::output()."</pre>");
    });
    // 3. Fresh Migration + Database Seeding (Wipes all data)
    Route::get('/db-fresh-seed', function () {
        Artisan::call('migrate:fresh', ['--seed' => true, '--force' => true]);
        return response("<pre>Database Wiped, Rebuilt & Seeded:\n\n".Artisan::output()."</pre>");
    });
});

// Authentication (Breeze) — /access/*
require __DIR__.'/auth.php';

// Authenticated Admin area — /access/*
require __DIR__.'/admin.php';

// Public Frontend Website / CMS — must be registered last so /{slug}
// can never shadow /access/*, /api/* or the routes defined above.
require __DIR__.'/frontend.php';
```

**Why this shape:**

- The three `/db-*` dev routes (a convenience used before SSH access was available on shared
  hosting) stay on top, guarded by **HTTP Basic auth** (`auth.basic`) so they are never public.
- `auth.php`, `admin.php`, `frontend.php` are **required in that order**. Since Laravel matches
  routes in registration order, the fixed-prefix routes win over the greedy `/{slug}`.
- The order `require auth → admin → frontend` is a convention that later phases keep.

#### 5b. **MODIFY** `routes/auth.php` — add the `access` prefix

Wrap Breeze's two existing groups with `Route::prefix('access')`. **Do not change any route names
or controller namespaces.**

```php
<?php

use App\Http\Controllers\Auth\AuthenticatedSessionController;
use App\Http\Controllers\Auth\ConfirmablePasswordController;
use App\Http\Controllers\Auth\EmailVerificationNotificationController;
use App\Http\Controllers\Auth\EmailVerificationPromptController;
use App\Http\Controllers\Auth\NewPasswordController;
use App\Http\Controllers\Auth\PasswordController;
use App\Http\Controllers\Auth\PasswordResetLinkController;
use App\Http\Controllers\Auth\RegisteredUserController;
use App\Http\Controllers\Auth\VerifyEmailController;
use Illuminate\Support\Facades\Route;

Route::prefix('access')->middleware('guest')->group(function () {
    Route::get('register', [RegisteredUserController::class, 'create'])
        ->name('register');

    Route::post('register', [RegisteredUserController::class, 'store']);

    Route::get('login', [AuthenticatedSessionController::class, 'create'])
        ->name('login');
```

```php
<?php

namespace App\Http\Controllers\Frontend;

use App\Http\Controllers\Controller;
use App\Models\Page;
use Illuminate\Database\Eloquent\ModelNotFoundException;
use Symfony\Component\HttpKernel\Exception\NotFoundHttpException;

class PageController extends Controller
{
    public function show(string $slug): \Illuminate\View\View
    {
        try {
            $page = Page::query()->published()->where('slug', $slug)->firstOrFail();
        } catch (ModelNotFoundException) {

        }

        return view('frontend.page', ['page' => $page]);
    }
}
```

**Why the try/catch?** `firstOrFail()` throws `ModelNotFoundException`, which becomes a **404** on
its own — but only if the model's not-found handler is registered. Being explicit guarantees a
clean `NotFoundHttpException` → 404 for *any* missing or unpublished slug. The end user sees the
standard Laravel 404 page either way.

### STEP 10 · API v1 authentication

The API needs exactly three endpoints: `POST /api/v1/login`, `POST /api/v1/logout`,
`GET /api/v1/user`. Because this is the *only* consumer of token logic and it is ~10 lines, the
implementation lives **directly in the controller** — no service class.

#### 10a. **CREATE** `app/Http/Requests/Api/V1/LoginRequest.php`

```php
<?php

namespace App\Http\Requests\Api\V1;

use Illuminate\Foundation\Http\FormRequest;
use Illuminate\Validation\Rule;

class LoginRequest extends FormRequest
{
    public function authorize(): bool
    {
        return true;
    }

    public function rules(): array
    {
        return [
            'email'    => ['required', 'email', Rule::exists('users', 'email')],
            'password' => ['required', 'string'],
        ];
    }
}
```

**Why `Rule::exists('users', 'email')`?** As a *first* response it lets us check the email
before touching the DB inside the controller. In PHASE 01 the controller still does its own
lookups (`where('email', ...)->first()`), which is fine.

#### 10b. **CREATE** `app/Http/Controllers/Api/V1/AuthController.php`

```php
<?php

namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use App\Http\Requests\Api\V1\LoginRequest;
use App\Models\User;
use Illuminate\Http\JsonResponse;
use Illuminate\Support\Facades\Hash;

class AuthController extends Controller
{
    public function login(LoginRequest $request): JsonResponse
    {
        $user = User::query()->where('email', $request->validated('email'))->first();

        if (! $user || ! Hash::check($request->validated('password'), $user->password)) {
            return response()->json([
                'message' => 'Invalid credentials',
            ], 422);
        }

        return response()->json([
            'token' => $user->createToken('api')->plainTextToken,
        ]);
    }

    public function logout(Request $request): JsonResponse
    {
        $request->user()->currentAccessToken()?->delete();

        return response()->json(['message' => 'Logged out']);
    }

    public function user(Request $request): JsonResponse
    {
        return response()->json([
            'user' => $request->user()->only('id', 'name', 'email'),
        ]);
    }
}
```

**What each endpoint does:**

| Endpoint              | Logic                                                        |
|-----------------------|--------------------------------------------------------------|
| `POST /api/v1/login`  | `LoginRequest` validates; we look the user up by email, `Hash::check` the password (stateless — no session), then `createToken('api')->plainTextToken`. |
| `POST /api/v1/logout` | `auth:sanctum` guards it; `currentAccessToken()?->delete()` revokes the token (the `?->` is safe when there is no token). |
| `GET /api/v1/user`    | `auth:sanctum` guards it; returns the token owner's `id`, `name`, `email`. |

**Why no `Services\Api\AuthService`?** In the first draft this logic lived in a service, but it
is used by exactly one controller and does not leave the controller context. Extracting it added
a class, a constructor, a namespace, and a mental hop for zero reusable benefit. **Keep the
inline version.** When a second consumer appears (e.g. a queue job, an OAuth-style token
exchange, or the admin acting on behalf of users), extract the logic into
`app/Services/Api/AuthService` exactly like the old pattern — the step would be (CREATE
service, MODIFY controller to inject it). See [7.7](#77-why-there-is-no-servicesactions-layer-yet).

## 7. Deep Dives

### 7.1 Route organization

<table>
  <tr><th>File</th><th>Content</th><th>Registered via</th></tr>
  <tr><td><b>routes/web.php</b></td><td>`/db-*` dev routes (auth.basic) + requires of auth/admin/frontend</td><td>web middleware group</td></tr>
  <tr><td><b>routes/auth.php</b></td><td>Breeze auth under `/access` (names unchanged)</td><td>required by web.php</td></tr>
  <tr><td><b>routes/admin.php</b></td><td>`/access/dashboard` + `/access/profile`</td><td>required by web.php</td></tr>
  <tr><td><b>routes/frontend.php</b></td><td>`/`, static pages, dynamic `/{slug}`</td><td>required by web.php (LAST)</td></tr>
  <tr><td><b>routes/api.php</b></td><td>prefixes `v1` to `routes/api/v1.php`</td><td>`withRouting(api: ...)` → `api` middleware group</td></tr>
  <tr><td><b>routes/api/v1.php</b></td><td>`POST /login`, `auth:sanctum` group → `/logout`, `/user`</td><td>required by api.php</td></tr>
</table>

**Why is `web.php` a *composer* of three files?**

- Every later phase keeps all admin routes in `admin.php`, all public/frontend routes in
  `frontend.php`.
- Anyone joining the project sees "everything under `/access`" in two short files instead of one
  growing `web.php` blob.
- The require order is deliberate: `auth.php` (guest + some auth middleware), then `admin.php`
  (`auth`/`verified`), then `frontend.php` — `/{slug}` is always last.

**Why is the API in `bootstrap/app.php` rather than `Route::prefix('api')` in `web.php`?**

`withRouting(api: ...)` gives API routes the framework's built-in **`api` middleware group**
(throttling, substitute bindings) with zero extra config, and it is resolved **before** the web
routes. Do **not** prefix API routes inside `web.php` — you would lose the dedicated middleware
group and put dynamic web routes in front of them.

### 7.5 API v1

```
POST /api/v1/login           (public, LoginRequest)
     ↓ username/password
     ↓ validate: email required|email|exists:users,email ; password required
     ↓ User::where('email', ...)->first()
     ↓ Hash::check(password) ? → createToken('api')->plainTextToken : 422 "Invalid credentials"
     → 200 { token }

POST /api/v1/logout          (auth:sanctum)
     → currentAccessToken()?->delete()
     → 200 { message: "Logged out" }

GET  /api/v1/user            (auth:sanctum)
     → 200 { user: { id, name, email } }
```

- **Stateless:** no session, no cookies. `Hash::check` never touches the `web` guard, so a browser
  user and an API client are fully isolated.
- **Token lifecycle:** login creates a Sanctum *personal access token*; logout deletes the one
  used (`currentAccessToken()`). Middleware `auth:sanctum` rejects requests without a valid
  `Authorization: Bearer` (→ 401).
- **Reasoning for `LoginRequest`:** route-level and action-level validation through a
  FormRequest keeps the controller tidy and gives a reusable ruleset.

### 7.6 Middleware

| Middleware            | Where                                                      | Effect                                        |
|-----------------------|------------------------------------------------------------|-----------------------------------------------|
| `auth.basic`          | `/db-*` dev routes                                         | HTTP Basic auth gate on database utilities    |
| `guest`               | Breeze guest routes (`access/register`, `access/login`, ...)| unauthenticated users may view/visit these   |
| `auth`                | Breeze authed routes + `/access/profile`                   | must be logged in (web guard)                 |
| `auth`, `verified`    | `/access/dashboard` and future admin modules               | logged in AND email verified                  |
| `signed` + `throttle:6,1` | email verification link                                | signed URL + brute-force protection           |
| `auth:sanctum`        | `/api/v1/logout`, `/api/v1/user`                           | must present a valid Bearer token             |
| `throttle` (api group)| all `/api/*` (framework `api` group)                       | rate limiting (default 60/min)                |

### 7.7 Why there is no Services/Actions layer yet

PHASE 01 deliberately ships **without** an `app/Services/`, `app/Actions/`, or `app/Support/`
folder. This is a *decision*, not an omission.

**The rule we follow:**

> Add an abstraction layer only when there is a real, identified second consumer — a second place
> that needs the same logic, or a rule complex enough to move out of the controller.

**Applying the rule today:**

| Logic                   | Where it lives                     | Why it stays there                                  |
|-------------------------|------------------------------------|-----------------------------------------------------|
| API login / tokens      | `Api\V1\AuthController` (inline)   | ~10 lines; exactly one consumer (the mobile app)    |
| Page selection (published scope) | `Page::scopePublished()`   | already reusable (controller + tests + future admin)|
| Profile update          | `Admin\ProfileController` + `ProfileUpdateRequest` | single consumer; rules are in the FormRequest |
| Static page rendering   | 6 one-method controllers           | rendering a view is not logic worth extracting      |

**What would justify extracting `app/Services/Api/AuthService` later?**

- A second consumer of `issueToken()` (a queue job, an admin impersonation flow, an
  OAuth-style exchange).
- Logic growing beyond a few lines (e.g. token refresh, device management, revocation
  workflows).
- Cross-controller/cross-job reuse of the same rule.

When that happens, the refactor is mechanical and *contained*:

1. **CREATE** `app/Services/Api/AuthService.php` with `issueToken(array $credentials): ?array`
   (`Hash::check` → `createToken('api')->plainTextToken`, or `null`) and
   `revokeCurrentToken()`.
2. **MODIFY** `Api\V1\AuthController` to inject it via constructor
   (Laravel's container wires it automatically) and call `$this->auth->issueToken(...)`.
3. Keep the **same** feature tests — the behavior must not change; only where the code lives
   changes.

Until that day, the ~10 lines stay in the controller where they are immediately visible.

### 7.8 Dynamic CMS route and route-conflict prevention

The risk: `GET /{slug}` matches **any** single-segment path. Without care, it would swallow:

- `/access/login`, `/access/dashboard`, `/access/profile`, ...
- `/api/v1/something` (web group wouldn't receive it anyway — it is registered under `api`)
- `/up` (health check), `/db-migrate`, ...

**Three lines of defense:**

1. **Registration order.** In `web.php` the requires run `auth.php` → `admin.php` →
   `frontend.php`, and inside `frontend.php` the static routes are declared **before** `/{slug}`.
   Laravel matches in declaration order, so `/access/dashboard` and `/about` are claimed *first*.
2. **The regex.** `->where('slug', '[a-zA-Z0-9][a-zA-Z0-9-_]*')` — slugs only start with
   alphanumerics and continue with letters/digits/`-`/`_`. `access`, `api`, `up` would all *match*
   the regex, so this alone is **not** enough — it only blocks paths like `favicon.ico.png`.
3. **api/health registration.** `bootstrap/app.php` registers the **api** routes via
   `withRouting(api: ...)` *before* the **web** routes, and `health: '/up'` is added before web as
   well. So `/api/*` and `/up` are claimed outside `web.php` entirely.

The net effect:

| Request            | Claimed by                     |
|--------------------|--------------------------------|
| `/`                | `frontend.home` (registered first) |
| `/about`           | `frontend.about` (static, before `/{slug}`) |
| `/access/...`      | auth.php / admin.php groups    |
| `/api/v1/...`      | routes/api/v1.php (api group)  |
| `/up`              | health route (before web)      |
| `/{anything else single segment}` | `frontend.page` → 404 if no published `Page` |

> When Phase 2+ adds more static URLs, the rule stays: **add them before `/{slug}`**.

## 8. Common Mistakes and Troubleshooting

| Symptom                                   | Likely cause                                                 | Fix |
|-------------------------------------------|--------------------------------------------------------------|-----|
| `GET /` → 404                             | `welcome.blade.php` deleted before `frontend.home` existed or `HomeController` view name wrong | Complete STEP 6 + 7 before STEP 12's deletes. `view('frontend.home')` file must exist. |
| `GET /` → 500                             | view file `resources/views/frontend/home.blade.php` missing  | Check the flat view file exists at `frontend/home.blade.php` (not inside a `home/` folder). |
| `GET /mission` → 404                      | slug has no `published` page (or `published_at` in the future / `status` != `published`) | Confirm via `Page::query()->published()->get()` |
| `/access/login` matches `/{slug}`         | `routes/frontend.php` required before `auth.php` in `web.php`, or slug regex removed | Order: auth → admin → frontend; keep `->where('slug', ...)` |
| `/access/dashboard` → 404                 | route name/controller moved but tests still use `get('/access/dashboard')` — should be fine; check `routes/admin.php` has the route | `php artisan route:list` and confirm `admin.dashboard` |
| `route('dashboard')` undefined            | forgot to rename to `admin.dashboard` in redirects or views | STEP 11; grep for `route('dashboard')` |
| Tests fail with 404    on `/login`        | `tests` hit `/multi-app-ecosystem-2/.../login` because `APP_URL` in `.env` has a sub-folder | `phpunit.xml` `APP_URL=http://localhost` (STEP 1) |
| Breeze tests fail on `dashboard`          | `ProfileTest`/`AuthenticationTest` still asserts `redirect()->route('dashboard')` | STEP 13 updated the redirected-to name; keep tests aligned |
| `POST /api/v1/login` → 500                | `AuthController` uses a service/method that doesn't exist | Controller must use `User::query()->where(...)`, `Hash::check`, `createToken('api')` inline |
| `GET /api/v1/user` → 401 always           | token missing/invalid, or user has no `HasApiTokens` trait   | STEP 4; send `Authorization: Bearer <token>` |
| `GET /api/v1/user` → 500 with "Column not found" | stale cached view/config, or DB migration not run | `php artisan optimize:clear`; `php artisan migrate` |
| Warns "cache" / old view rendered         | compiled views or config cached from before file moves       | `php artisan optimize:clear` (after every big move) |
| Feature test uses the old reset link      | `PasswordResetTest` hard-codes `/reset-password/{token}`     | prefix → `/access/reset-password/{token}` |
| Routes show 35 but `/{slug}` missing      | `where` constraint regex missing                            | keep `->where('slug', '[a-zA-Z0-9][a-zA-Z0-9-_]*')` |
| `view('frontend.pages.show')` not found   | copied old nested structure from an earlier draft            | flat file: `frontend/page.blade.php` (singular, no `pages/`) |
| `/api/v1/user` returns HTML instead of JSON | `shouldRenderJsonWhen` removed or an exception happened in web context | keep the `withExceptions` block from STEP 5g |
